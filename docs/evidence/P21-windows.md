# P21 — modern Windows menu and installation lifecycle

**Status:** implementation complete; one qualification step remains human-gated.
**Date:** 2026-11-12. **Host:** Windows 11 25H2 (build 26200), x64, non-admin user,
node v26.13.1, Electron 45.3.0.

## What was delivered

- **`native/windows-shell/`** — a 239 KB x64 COM DLL (`MonaMenu.dll`) that implements
  `IExplorerCommand` and nothing else. It resolves exactly one selected folder,
  refuses files, multi-selections, and unquotable names, and starts Mona with
  `"<Mona.exe>" project open --path "<folder>" --profile ds-full-access` through
  `CreateProcessW` with the executable as `lpApplicationName`. No shell string is
  built, no network call is made, no model work exists in the helper. It also
  carried no reference to any inference or networking API — checked in tests.
- **`native/windows-shell/mona-menu-probe.c`** — a real-process harness that loads
  the DLL through `DllGetClassObject` *and* through `CoCreateInstance`, builds a
  genuine `IShellItemArray`, and prints JSON.
- **Sparse identity package** — `AppxManifest.xml` generated by the installer with
  `uap10:AllowExternalContent`, `runFullTrust`, a `windows.comServer` entry for the
  CLSID, and `windows.fileExplorerContextMenus` verbs for `Directory` and
  `Directory\Background`. Package logos are generated deterministically as PNGs.
- **`tools/install/`** — per-user lifecycle: `stage`, `package`, `sign`,
  `trust-test-certificate`, `install`, `upgrade`, `uninstall`, `status`, `verify`.
  Every staged file is checksummed (1,656 files); installation is atomic
  (`.new-<stamp>` → rename swap), idempotent, and removes only Mona-owned keys and
  directories.
- **`apps/desktop/src/main/install-gate.ts`** — the app publishes
  `runtime/activity.json` (`pid`, `state`, `runState`, `projectId`) so an upgrade can
  distinguish "not running" from "work in flight". It is local state only and a
  failed write never fails a task.
- **Packaged-argv fix** — the installed build exposed a real bug: Electron reports
  `[Mona.exe, <install>\resources\app, project, open, ...]`, and `stripLauncherArgs`
  previously stripped the app directory only when unpackaged. The first packaged
  launch probe therefore opened a project literally named `app`. `stripLauncherArgs`
  now removes the app directory in both modes, with tests for the packaged shape, a
  look-alike folder, and the unchanged unpackaged behaviour.

## Modern menu: built, signed, not yet registered

The identity package is produced and test-signed:

- `Mona-0.1.0-x64.msix` sha256 `3a397745a901a11020976da96e3cc6b86227eb4f7014bd2dd3eee11a88a95c2c`
- Signing certificate `CN=Mona Development`, thumbprint `5C0AD0D7…`, labelled
  **test-only**, not timestamped, no production identity.
- `signtool verify /pa` reports an untrusted root, which is the accurate status.

Registration is refused by Windows, and the exact outcomes were observed:

1. Unsigned sparse registration (`Add-AppxPackage -Register … -ExternalLocation …`):
   `0x80073CFF` — "need either a Windows developer license or a sideloading-enabled
   system".
2. Test-signed package (`Add-AppxPackage -Path … -ExternalLocation …`): `0x800B0109`
   — "The root certificate of the signature … must be trusted". The manifest itself
   passed schema validation, since that error is raised only after the manifest is
   accepted.
3. `Import-Certificate -CertStoreLocation Cert:\CurrentUser\Root`:
   "UI is not allowed in this operation"; `certutil -addstore -user Root` waits for a
   Windows consent dialog and had to be cancelled.
4. `-DevelopmentMode` is not an available parameter on this `Appx` module; developer
   mode itself is an `HKLM` policy and needs administrator rights, which this
   account does not have.

Therefore the modern menu is **built and its COM contract is verified, but the
entry cannot appear in Explorer until one of these happens** — Victor's decision:

- **A.** Enable Windows developer mode (administrator, one time), then run
  `node tools/install/cli.mjs install` again (unsigned manifest registration).
- **B.** Run `node tools/install/cli.mjs trust-test-certificate` in an interactive
  terminal and accept the Windows security warning for the labelled test
  certificate (current-user Root store; uninstall removes it).
- **C.** Provide a production code-signing certificate and sign with
  `MONA_SIGN_PFX` (plus `MONA_SIGN_PASSWORD`, optional RFC 3161
  `MONA_SIGN_TIMESTAMP`). That path is implemented and never stores the
  certificate in the repository; it has not been exercised because no such
  certificate exists here. The manifest publisher is `CN=Mona Development` and
  must match the certificate subject.

Until then the classic per-user menu remains registered (verified pointing at the
installed `Mona.exe`) and is **not** presented as the modern menu.

## Signing and distribution status

- No production signature exists and none is claimed. `signingStatus` in
  `P21-package.json` says "test-signed with a self-created certificate; not a
  production signature".
- No trust root was added silently: the Root-store import was refused by Windows and
  is exposed only as a separate, explicit command.
- Checksums are written to `%LOCALAPPDATA%\Mona\artifacts\SHA256SUMS-0.1.0.txt`.
- No public artifact, repository, package, or purchase was created.

## Residual issues

- **P21-ISSUE-001** — Explorer has not been seen rendering the modern menu; that is
  blocked by the trust gate above. No screenshot of the modern menu exists, and none
  is implied.
- **P21-ISSUE-002** — No Windows VM was available; all evidence is from this host.
- **P21-ISSUE-003** — Identity package registration blocked (see above).
- **P21-ISSUE-004** — The packaged app keeps the `@mona/desktop` application
  identity, so the installed app reads the same user data as development runs.
  Renaming the product identity would move the profile and is deliberately out of
  scope; recorded in `DECISIONS.md`.
- **P21-ISSUE-005** — The staged payload is 452 MB because Electron's full `locales`
  directory is copied; pruning is a release-packaging task, not a correctness issue.
- **P21-ISSUE-006** — The installed uninstall removes its own program directory from
  a detached command after the process exits; the evidence checks the directory
  after a wait rather than observing the exact instant.

  `IExplorerCommand`, sparse packages), updated 2026-07-17: manifest namespaces,
  `com:SurrogateServer`/`com:Class`, `desktop5:ItemType` values, and the
  `uap10:AllowExternalContent` sparse-package shape.

- Microsoft, *Grant identity to non-packaged desktop apps*: signing requirements,
  `CERT_E_UNTRUSTEDROOT` behaviour, and the Trusted People guidance.
  <https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-non-packaged-apps>

  BuildTools MSIX tools 10.0.28000.2957, both pinned and SHA-256 verified through
  `tools/install/fetch-tools` notes recorded in `.mona/build/DECISIONS.md`.
